## 0. 运营者定的语法（原话照录）

> 1. 不使用 `$$` 包裹表示全局搜索，即标题、标签等都进行搜索
> 2. 多层嵌套 `$$` 或者解析失败也视为全局搜索
> 3. 使用 `$[-]tag:[%]Value$` 进行匹配，`-` 表示不含，`tag` 为标签，其他的标题等都可以作为可选字段，
>    `Value` 为匹配内容，可使用 `%` 进行模糊匹配、`_` 为单字模糊匹配，使用 `[]` 包裹可将模糊匹配字段
>    视作普通字符进行匹配；点击标签时自动在标签栏添加匹配，默认全字匹配进行过滤，多个过滤条件通过空格区分。

**我的解读**（下面 §2 是正式定义，若与你的本意有出入，改这里就行）：

| 运营者的话 | 落到实现 |
|-----------|---------|
| 不用 `$$` 包裹 = 全局搜索 | 框里没有 `$…$` 块时，整串是自由文本，按全局字段搜索（今天的默认行为） |
| 嵌套 `$$` / 解析失败 = 全局搜索 | 解析器**从不报错**；解析不出来的那段退化为自由文本、其余块照常过滤（分段退化，§2.4） |
| `$[-]tag:[%]Value$` | 块内每个条件 `[-]字段:值`，空格分隔；`-` = 不含 |
| `其他字段都可以作为可选字段` | 字段表用**和规则编辑器同一份**字段词表（`app/api/settings.py` 里那份），不是另写一张（§2.2） |
| `%` / `_` / `[…]` | 块内为通配：`%` 任意多字符、`_` 单个字符、`[%]`/`[_]` 是字面量（与规则 DSL 的 LIKE 完全同语义） |
| 默认全字匹配 | 值里**没有**通配符时按「整体相等」比（标签 = 整个标签、分类 = 整个分类、标题 = 整个标题）；要模糊就写 `%` |
| 点击标签 → 标签栏添加匹配 | 点任意地方的标签，把 `$tag:值$` 追加进搜索框并提交；搜索框下方渲染当前条件 chips（§3） |
| 多个过滤条件用空格区分 | 空格 = 条件分隔符；块内是 AND，块与块之间也是 AND |

## 1. 现状与成因（为什么必须改）

**搜索结果为什么「不准」**（代码事实，`app/db/database.py`）：

- 候选列表 `_list_candidates_page_sync`：一个 `LIKE '%关键词%'` **子串**，一次扫
  `Title`、`JapaneseTitle`、`Artist`、`Group`、`Tags`、`TagsRaw`、`ArtistRaw`、`GroupRaw` 八个字段；
- 已下载列表 `_list_downloaded_works_sync`：同上少两个 Raw 字段，另加「来源」（provider 代码/中文名，见
  `app/api/status.py` 的 `provider_codes_matching`）；
- 所以搜 `NTR`：**标签里没有、标题里也没有**也能命中——作者/社团/日文标题里的 `ntr` 算命中
  （`Artist` 与 `ArtistRaw` 还等于同一事实被匹配两次），`entry`/`country`/`introduction` 这种**子串**也算命中；
- 关键词是**整串**比较（`%整串%`），「两个词」几乎搜不到。

**侧栏 facet 反倒是精确的**：标签用逗号围栏（`_FACET_CONTAINS_SQL`），单选字段用 `IN`；
但侧栏只列 **24 个**值（`CANDIDATE_FACET_LIMIT`），超出部分今天只能靠搜索框——而搜索框正是最不准的入口。

## 2. 语法定义

### 2.1 形式

```
query      := (free-text | block)*
block      := "$" condition (" " condition)* "$"
condition  := ["-"] field ":" value
value      := (char | wildcard | escape)+      # 引号见下
wildcard   := "%" | "_"                        # % 任意多、_ 单个
escape     := "[%]" | "[_]"                    # 字面量的 % 和 _
```

- 块外的文本 = **自由文本**（全局搜索）；按空格切成多个词，词与词 AND（今天的「整串比较」改为多词 AND）；
- 块内条件之间 AND；块与块之间 AND；自由文本的多个词也是 AND（运营者定：**多个条件均为 AND**）；
- 带空格的值用**双引号**包起来：`$tag:"sole female"$`（运营者定：**接受双引号**；标签栏自动插入时就这么写）；
- 自由文本里的 `%` / `_` **同样是通配符**（运营者定：自由文本里的内容也当通配），要字面量就写 `[%]` / `[_]`。

### 2.2 字段表

字段名复用**规则编辑器同一份词表**（`app/api/settings.py` 生成的 `vocabulary.fields`，也就是
`app/auto_approval/rules.py` 的 `ALLOWED_FIELDS`）**扣掉数值字段**（见下），因此不会出现第二张会漂移的清单。常用：

| 写法 | 含义 | 匹配对象 |
|------|------|---------|
| `tag` | 标签 | `Tags`（中文译名）+ `TagsRaw`（上游原名，去 `namespace:` 后也认） |
| `title` / `jtitle` | 标题 / 日文标题 | 单值 |
| `artist` / `group` | 作者 / 社团 | 多值（逗号分隔，逐项比较） |
| `category` / `language` | 分类 / 语言 | 单值 |
| `parody` / `character` | 原作 / 角色 | 多值 |
| `uploader` | 上传者 | 单值 |
| `source`（仅已下载） | 来源 | provider 代码或中文名（复用 `provider_codes_matching`） |
| `status`（仅候选） | 候选状态 | 状态码 |

**数值字段（`pages` / `rating` / `filesize`）不做搜索过滤**（运营者定：数值字段不考虑过滤匹配），
所以本方案在词表里**去掉这几项**；`status`（候选）与 `source`（已下载）**保留**
（运营者定：要加上候选与来源过滤）。

### 2.3 匹配语义

- **默认（值里没有通配符）= 整体匹配**：多值字段逐项相等（`tag` 走逗号围栏，`sole female` 不会命中
  `sole female only`），单值字段整个字段相等；
- `%` / `_` 出现时按 LIKE 语义模糊（`$tag:%cosplay%$` 命中任何含 cosplay 的标签）；
- `[%]` / `[_]` 是字面量（与规则 DSL 的写法一致，两边同一个帮助文案）；
- **大小写**：ASCII 不区分（SQLite `LIKE` 语义），中文无大小写；
- `-` 前缀 = 不含（`$[-]tag:ntr$` = 没有 ntr 标签）；
- 自由文本：子串匹配（标题要能搜片段），`%`/`_` **同样是通配**（运营者定）。

### 2.4 解析失败的退化（运营者定：分段退化）

运营者 2026-10-08 定：**分段退化**——解析不了的**那一段**当自由文本、按全局搜索处理，其余能解析的块
**照常过滤**，解析器**绝不报错**。这同时满足运营者规则 2（`$` 解析失败 → 全局搜索）：坏掉的部分确实
走了全局搜索，只是不牵连旁边的合法条件（asmr.one 也是逐词兜底，§2.6）。

- `$tag:ntr$ $$坏$` → `tag` 块照常过滤，`$$坏$` 这一段降级为自由文本；
- `$tag:ntr`（只有半个）→ 整段降级为自由文本，等价于整条退化为全局搜索；
- 搜索框下方给一行提示，列出被降级的片段：「`$$坏$` 解析失败，已按全局搜索处理」。

### 2.5 与今天不同的地方（可能影响你现在的习惯）

1. 多个词从「整个字符串」变成 **AND 多个词**（「ntr cosplay」今天搜不到，之后是「两者都要有」）；
2. `%` / `_` 从「当普通字符」变成**通配符**（要字面量写 `[%]` / `[_]`）——只影响这两个字符本身；
3. `-` 开头变成「排除」；
4. `字段:值` 只在 `$…$` 里生效，自由文本里的冒号仍是普通字符（不会被误当过滤）；
5. 数值字段（`pages` / `rating` / `filesize`）**不参与过滤**（运营者定）；
6. 解析失败从「整条失效」改成**分段退化**（§2.4）。

### 2.6 与参考站 asmr.one 的实际对照（2026-10-08 抓线上 bundle）

之前只在文首引用了运营者那句话，**没有真的去看站点的实现**。现已抓 `https://www.asmr.one/js/app.c5f7e7ac.js`
反查其搜索词法（`SearchKeywordService.parseMulti` / `parseSingle`、`KeywordTermType` 四个枚举），结论是
**运营者的 `$…$` 写法就是 asmr.one 的写法**，逐条对得上：

| asmr.one 实际实现 | 说明 | 本方案 |
|-------------------|------|--------|
| `$ns:value$`（`FullSpecial`） | 首尾都有 `$` 的完整块 | 同（§2.1 `block`） |
| `$-ns:value$` | `-` 前缀 = 排除 | 同（§2.1 `["-"]`） |
| `$ns` / `$-ns`（`PartialSpecial_Namespace`） | 还没取值的半成品块（输入中弹建议用） | 本轮不单独处理，按解析失败退化 |
| `$ns:value`（`PartialSpecial_Value`，只有一个 `$`） | 输入中的半成品值块 | 同上 |
| 自由文本（`PlainKeyword`） | `-词` 排除；`"带空格的值"` / `'…'` 引号 | 同（§8 待定 3、4） |
| 词表 `tag`/`t`、`tagw`/`tw`、`circle`/`c`、`va`/`v`、`rate`、`price`、`sell`、`age`、`duration`/`d`、`lang` | 且**接受短别名** | 用 EhBot 自己的字段表（§2.2），别名要不要跟见下 |
| `rate` / `price` / `sell` / `duration` 是**数值比较** | 正号 = `>`，`-duration` = `<` | **不做**（数值字段不参与过滤，§8-6） |
| `age` 是枚举（`general` / `r15` / `adult`），如 `$-age:adult$` | 预设 caption（`optionsCaptionByValue`） | 对应 `category` / 自有枚举 |
| 解析不出来的 `$` 一律当**普通文本** | `parseSingle` 兜底返回 `PlainKeyword`，从不报错 | 同（运营者规则 2，§2.4） |
| 词与词按出现顺序、AND 组合 | `parseMulti` 先抠 `$…$` 块、再抠引号串、再按空格切，最后按原位置排序 | 同（§2.1） |
| 客户端把**原始字符串**发给 `/api/search/<keyword>`，解析在服务端 | 前端解析器只用于输入建议 | 本方案在服务端解析（§4） |
| 常驻「全局筛选」用**同一套语法**、前缀在关键字前 | `keyword: (globalFilter||"") + " " + keyword` | 本仓库没有这层，不在本轮 |
| 点标签 →「🔍 过滤」/「🚫 排除」；长按标签 → 更多信息；「🔃 反转」把条件在过滤/排除间对调 | | 本方案做「🔍 过滤 / 🚫 排除」两个动作（§3.2）；**反转 / 永久排除不纳入** |

**两处「asmr.one 有、按运营者口径本方案没跟上」的地方**（列出来供你判断）：

1. **通配符**：asmr.one **没有** `%` / `_` / `[%]`——它的标签值是精确值（配输入建议选）。
   `%`/`_`/`[…]` 这层语义来自本仓库**自动审批规则 DSL**，运营者规则 3 把它引进了搜索块，故保留；
   但要清楚「默认整体匹配」是运营者新增、不是 asmr.one 的行为。
2. **数值比较**：asmr.one 的数值字段就是 `>`（`-` 则 `<`）。**但运营者已定：数值字段完全不参与过滤**
   （`=`、`>`、`<` 都不做，§2.2 / §8），所以本方案在这点上有意与参考站不同。

## 3. 界面：标签栏（chips）与「点标签即过滤」

1. **标签栏**：搜索框下方渲染当前**解析成功**的条件 chips：`标签 = NTR`、`不含 标签 = cosplay`、
   `标题 ≈ %天使%`——**全字/模糊显式区分**（运营者定：可以显示；`=` 全字、`≈` 模糊），每个右上角一个 ×
   （纯链接，删掉对应条件后重新提交；no-JS 可用）。被降级的片段在那一行提示「…解析失败，已按全局搜索处理」（§2.4）。
2. **点标签 = 两个动作**（运营者定：要有过滤与排除两个动作，同 asmr.one）：候选卡片/列表、作品详情页元数据、
   已下载卡片的标签，点一下给「🔍 过滤」/「🚫 排除」两个动作——过滤追加 `$tag:值$`、排除追加 `$-tag:值$`
   （值为中文译名；带空格用双引号），追加后提交；已在搜索框里的同一个条件不重复添加。
   > asmr.one 的「🔃 反转」与「⛔ 永久排除」**不纳入本方案**（运营者定）。
3. **侧栏 facet 保持现状**：侧栏点选仍写 query string 且高亮；chips 只反映搜索框里的条件，两者互不覆盖
   （把侧栏塞进同一套 chips 属于 §5 延后那批）。
4. **命名空间标签**：卡片显示的是中文译名，所以点击插入 `$tag:中文译名$`；`TagsRaw` 的 `female:netorare`
   在 `tag` 字段里同时接受「带命名空间」与「去掉命名空间」两种写法（§2.2）。

## 4. 落在哪里

- 新模块 `app/search/query.py`：`parse_query(text) -> ParsedQuery(filters, free_terms, degraded)` 与
  `candidate_sql(...)` / `downloaded_sql(...)`（把条件编译成 `EXISTS (SELECT 1 FROM metadata_values …)`

  > **落地偏差（2026-10-08）**：载荷键实际叫 `search_filters`，不叫 `filters`——候选端点上 `filters`
  > 已经是侧栏 facet 的选择（`{name: [values]}`），两个语义共用一个名字会被读成同一件事。

## 5. 不做 / 仍延后

- 不做 FTS5 全文索引；不做布尔 `OR` / 括号（多词已经是 AND，需要 OR 就分两次搜）；
- 数值字段不做过滤（运营者定；连 `=` 都不做）；
- **仍延后**（沿着 §3.3 的记录）：已下载页的 facet 侧栏、facet 上限 24→200、「归档文件名 / 库内相对路径」
  纳入已下载搜索。运营者的新语法在「标签栏」这层已经覆盖了侧栏最常用的用法，所以这批继续排后面。
