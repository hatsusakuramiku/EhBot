# 方案：WebUI 全局局部刷新与 WebSocket 状态同步（R86 扩展）

**状态：已实现 v4（2026-10-12）。** 运营者已明确要求「先做好并实现 web 端与服务端的 API，后续移动端的实现使用这些 API 就行了」。R86 完成服务端协议、WebUI、测试和接入契约；移动端代码在后续阶段实现，本轮不修改移动端仓库。本方案承接 `TAG_FILTER_CONTEXT_MENU_PROPOSAL.md`。

**运营者已定边界：** Web 端和移动端目前均为测试阶段，尚未达到 release 条件。两端最终均使用 WebSocket，先交付服务端与 WebUI，再由移动端接入；API 能复用就复用，妨碍实现的接口可以重写。审核、下载、打包、元数据同步等仍复用既有服务。

## 1. 需求结论

目前页面并非“只有轮询”：已有 HTMX 局部替换、`/api/v1/events` Server-Sent Events，以及候选/已下载/活动/作品详情等页面的 JSON 轮询，但各页面的操作响应和刷新策略不一致。许多 HTML POST 路由仍返回 303，操作后会整页导航；部分后台任务只能等轮询或手动刷新才能看到结构变化。

目标是统一成以下体验：

1. WebUI 的操作默认只更新受影响的内容区或行，不整页刷新。
2. 例如点击“重新打包”后，按钮立即进入处理中状态；打包任务状态、进度、错误和完成结果由后台主动推送，前端自动更新对应区域。
3. 前台仍可提交操作给后端；后端每次状态变化都向已连接页面发送事件，页面按事件更新或重新取得当前片段。
4. WebSocket 作为双端实时通道，替代页面状态轮询；断线显示连接状态、自动重连，并在重连后校正快照，不用定时刷新整页掩盖断线。
5. Tag 的左键过滤和右键菜单也使用同一局部刷新通道，地址栏不因筛选操作改变。
6. WebUI 和 `EhBot-Mobile` 都使用同一套 WebSocket 命令/事件协议；现有 API 能保留的继续保留，确实阻碍统一协议的写接口可以在测试阶段重写，并同步更新移动端。

## 2. 现状证据与问题

- `base.html` 已把 `#main` 设置为 HTMX 目标，且 `deps.page_layout()` 能在 `HX-Request` 时返回 `_fragment.html`；这是统一局部刷新所需的基础。
- 候选、已下载、活动、作品详情和日志各自拥有脚本。活动页、日志页、作品详情已有 SSE 订阅；已下载页和部分页面仍按 `/api/v1/...` 定时轮询，候选页主要依赖操作后的页面响应。
- `app/api/events.py` 已有带序列号、队列上限、断开清理和心跳的 `EventBus`，当前输出格式是 SSE；多个服务和路由已经发布 `candidate`、`download`、`conversion`、`connection` 事件。
- 许多 Web 路由的成功分支返回 `RedirectResponse`，错误也按整页模板重新渲染；表单没有统一的 HX 成功/失败响应约定。
- 现有事件只携带少量 ID，客户端遇到行新增、离开当前分组或结构变化时只能提示“刷新查看”或等待下一轮轮询，不能可靠地自动更新整个局部页面。
- 已读取 [EhBot-Mobile](https://github.com/hatsusakuramiku/EhBot-Mobile) 的远端 HEAD `dd37ac9ef1d92e189fade5bd385c519d12bd85e7`（临时只读审阅副本）。`lib/api/events.dart` 是 SSE 客户端，`lib/state/live_monitor.dart` 在断流后回退定时 tick，`lib/ui/home_shell.dart` 持有监视器并向子页传递更新。每个事件只发通用 tick，页面各自重新查询，缺少实体级更新。
- 移动端 `lib/api/auth_session.dart` 的 `bearer` 同时支持密码登录后的 access token 与 API Key，WebSocket 必须覆盖两种登录。`ehbot_api.dart` 及模型、日志页、连接提示和测试都需要同步调整；实际移动端测试基线须在实现时重新运行，不把 PHASES 中的 204 条记录当成当前已验证结果。

## 3. 设计原则与范围

### 3.1 双向 WebSocket 分工

WebUI 与移动端都通过同一条 WebSocket 连接发送操作命令、接收确认和状态事件。HTTP API 保留为登录/刷新凭据、初始快照、缩略图和文件传输等适合请求/响应的边界；写 API 如能调用同一业务入口则保留，重复或妨碍统一协议的接口可以重写或移除，并同步修改两端调用、测试和契约文档。

- 客户端命令统一为 `{type:"command", request_id, name, payload}`；`request_id` 用于关联确认与结果。同一连接最近 4096 条内拒绝重复 ID，不持久化去重；回复丢失时先查询操作/实体状态，不能自动重发删除、重下载、花费 GP 等写操作。
- `command.accepted` 只表示请求已接收；`command.result` 表示写入已提交或任务已入队，`command.error` 表示拒绝或失败。业务提交后再广播 `state`；任务的后续进度/完成/失败按相同实体更新流推送，不能把“收到确认”显示为“打包完成”。
- WebUI 的表单不再直接依赖 303；脚本把表单值转换为命令，收到确认和状态事件后更新行、卡片、抽屉或当前列表片段。无 WebSocket 时才退回普通 HTMX/HTTP 表单。
- 移动端直接复用同一命令名、参数、错误码和状态事件，不再为移动端维护一套轮询动作接口。

浏览器连接使用会话 Cookie，并在 `hello` 中携带当前页面 CSRF token；服务端同时校验同源 `Origin`。移动端使用现有 Bearer access token 或 API Key，不发送 CSRF token。refresh token 只用于 HTTP 刷新接口，绝不放进 WebSocket 帧或 URL。

### 3.2 局部刷新边界

所有带操作按钮的已登录页面纳入统一规则：候选、已下载、活动、作品详情、连接、设置、自动审批、归档设置和手动添加等。

- 普通导航、登录、退出登录、改密码后的会话切换仍允许整页导航。
- 操作和状态变化统一读取原 Jinja 页面片段，替换当前 `#main` 内容；能确认未变化的行沿用原节点。不维护第二套客户端实体渲染器；日志及元数据抽屉继续更新自身区域。
- 列表片段替换前保留仍存在的勾选、焦点、滚动位置和抽屉上下文；未提交的编辑表单用 `hx-preserve` 保留原节点。详情页重打包自动更新状态与动作，保留其他元数据输入；后续移动端更新对应实体与控件，不把每条事件转成整个页面的 loading。
- 后台事件只更新当前页面能识别的实体；当前页没有该实体时不盲目插入不完整行，而是收到 `refresh_required` 后按当前界面状态重新请求片段。
- 所有局部请求不修改地址栏和浏览器历史，除非该控件本来就是导航或用户明确改变了页面路由。

### 3.3 HTML 片段与 HTTP 保留入口

为 HTML 操作路由建立统一 HX 约定：

- 操作路由保留现有验证和 303；WebSocket 命令桥在进程内调用原路由、受限跟随同源 GET 重定向并取得 `HX-Request: true` 片段。普通 HTTP 请求继续原有行为，浏览器的 HTTP 降级同样使用 HX 片段。
- 400/422 返回包含错误提示的局部内容并保留用户输入；401 仍跳转登录；5xx 不伪装成成功。
- 命令结果用 `request_id` 关联，前端按钮在请求期间禁用，收到成功/失败后恢复；HTTP 降级也保留按钮锁定与当前界面查询。
- 不让每个路由自行拼接 JS；局部 HTML 由现有 Jinja 模板和共享宏生成，页面脚本只负责交互和事件绑定。

### 3.4 WebSocket 协议

新增已认证的 `/ws/ui`：

1. 浏览器用会话 Cookie 建立连接，移动端用现有 `Authorization: Bearer <access-token 或 API Key>` 建立连接；两种方式都经过同一管理员权限守卫，服务端不接受未认证连接。路径解析遵循既有服务器 base URL/反向代理前缀，HTTP/HTTPS 对应 WS/WSS。
2. 客户端第一帧发送 `hello`，包括 `protocol="ehbot-realtime.v1"`、`client="web"|"mobile"`、`logs`；浏览器同时发送 CSRF token。暂不提供按最后序列重放。
3. 服务端发送 `ready`，包括协议版本、epoch、当前序列、心跳间隔、`replay:false` 和有限命令目录；认证后的 `GET /api/v1/realtime` 也提供目录。
4. 状态事件统一为 JSON：

   ```json
   {
     "type": "state",
     "epoch": "进程标识",
     "sequence": 123,
     "scope": "download",
     "data": {"candidate_id": 42, "job_id": 9},
     "refresh_required": true
   }
   ```

5. 事件是失效通知，携带已知实体 ID；客户端读取权威 HTML/JSON 快照再更新进度、错误与动作可用性。状态标签仍来自服务端词表，不由 JS/Dart 自己翻译，也不新增实体 revision。
6. 业务事件本身不判断某个客户端的筛选结果；客户端按当前订阅/筛选上下文判断是否需要更新列表、数量或分组，无法判断时发起一次快照校正。WebUI 复用 HTML 片段，移动端复用 JSON 模型。
7. 连接断开时带抖动指数退避重连；重连后必须快照校正。EventBus 不重放事件；先订阅，再读快照，保守水位取读取前的全局 sequence，期间较新通知要求再次校正。服务端重启用 epoch 区分序列，不能把全局序列当实体版本。
8. 发送队列有界，进度事件可合并最新值；慢客户端要求快照或断开，不能阻塞业务。WebSocket 心跳及后端采集 qBittorrent/Telegram 状态的轮询与“页面轮询刷新”分别处理，后者删除不代表前者停用。

WebSocket 协议与 WebUI HTML 解耦：移动端只允许 `api.*` JSON 命令、状态事件和快照，不接收 Jinja/HTMX 片段。协议不匹配时返回 `PROTOCOL_UNSUPPORTED` 并关闭连接。

### 3.5 轮询与 SSE 的处理

- 双端删除定时页面状态轮询，断线显示“重连中”，保留已有内容并允许主动取得快照，不以整页 loading 循环代替实时连接。
- EventBus 和日志 broker 复用为 WebSocket 事件源；双端同时迁移状态和日志 SSE 的调用，保留 SSE 接口只取决于是否仍有明确用途，不设旧测试版兼容窗口。
- `/api/v1` 快照接口保留用于初始加载、重连、结构变化及主动刷新。事件触发的一次查询不是定时轮询；优先直接应用实体变更，密集事件合并查询。

### 3.6 EhBot-Mobile 同步实施

- `/api/v1/auth/login`、`refresh`、`logout`、`whoami` 继续保留，Bearer 令牌轮换和错误码保持稳定；WebSocket 不要求移动端使用 Cookie 或 CSRF。
- 优先复用 `/api/v1` 列表信封、分页、`search_filters`、状态视图和错误信封；若需要改变，先同步移动端 `CONTRACT.md`、Dart 模型、调用和双端测试，不能以“旧版必须兼容”为由延后本阶段目标。
- 新增 WebSocket 命令/事件使用 `ehbot-realtime.v1`，稳定字段包括 `request_id/sequence/scope/entity/id/revision`；移动端必须实现握手、命令确认、断线重连和快照校正。
- 新协议使用明确版本，字段重命名/删除可在测试阶段同步调整两端；未知可选字段可忽略，未知协议必须提示版本不匹配。命令和事件各有固定模型，不执行动态路径或任意方法调用。
- 移动端替换 `SseEventSource` 与 `LiveMonitor` 的通用 tick 模式，在 `HomeShell`/会话层持有一条连接，按实体更新数据；日志页订阅同一连接的日志消息。切换服务器、退出或更换凭据先取消旧订阅并关闭连接，晚到的旧响应不得写入新服务器页面。
- App 进入后台可以暂停连接，不承诺移动系统后台永远保活；恢复前台自动重连及快照校正。access 到期按现有逻辑只刷新一次再重连，API Key 吊销直接提示重新认证，不能调用 refresh；活跃连接也须感知吊销/到期。
- 移动端仓库的实现、测试和发布必须与后端同步；本仓库交付协议、示例帧和兼容测试，移动端仓库交付 WebSocket 客户端、命令映射和回归测试，两个仓库记录配套版本。

## 4. 分步实施边界

R86 内按以下三个步骤验证服务端与 WebUI，交付移动端所需的协议与命令目录。以下涉及移动端代码、Flutter 测试和真机联调的事项均为后续移动端阶段的验收条件，不阻塞 R86 交付。

### R86-A：全局局部操作基础

- 复用 HX 片段布局和业务路由，经统一命令桥处理成功/失败及重定向；改造候选、已下载、活动、作品详情的审核、下载、重新打包、重命名、元数据保存操作。
- Tag 页面内过滤纳入该基础：左键追加过滤条件，右键选择过滤/排除，HTMX 更新 `#main`，地址栏不变。
- 其余设置类表单保留原行为，先完成响应约定和测试工具。

### R86-B：双端 WebSocket 协议与命令通道

- 增加 `/ws/ui`、双端认证、hello/ready、命令确认、重复请求规则、心跳、序列、重连、快照校正和事件协议；将同一 `EventBus` 适配到 WebSocket。
- WebUI 接入命令与状态，两个已连接客户端验证重新打包认领和完成事件；交付移动端的认证/JSON 命令能力，移动端客户端后续实现。
- 复用或同步改写既有 API，验证并发页面、慢客户端、重复命令和事件丢失后的快照修正。

### R86-C：WebUI 全部页面与接入契约收口

- 把连接、候选、自动审批、归档设置等剩余写操作接入统一命令和局部响应；按页面实际结构更新区块。
- WebUI 停止页面轮询和 EventSource，状态及日志统一 WebSocket；HTTP API/SSE 保留供既有客户端过渡，移动端后续替换自身实时实现。
- 同步文档、代理升级配置及现有订阅/丢弃统计入口；不新增外部监控服务。
- 交付 `ehbot-realtime.v1` 契约、示例帧、服务端/WebUI 回归与阶段记录；移动端仓库后续登记配套实现和设备验收。

若任一步骤暴露出某个页面需要完整重渲染才能保持业务正确，允许该页面暂时使用 `refresh_required` 的片段刷新，不为它另造客户端状态模型。

## 5. 安全、可靠性与兼容性

- WebSocket 支持会话 Cookie、Bearer access token 和 API Key；浏览器校验同源 Origin/CSRF，原生移动端校验 Bearer，不要求浏览器 Origin。每条命令复用既有业务验证、检查认证有效性和重复请求规则。
- 不在事件中发送密码、Token、Cookie 或完整敏感配置；事件只包含状态、ID、版本和必要的公开展示字段。
- 连接断开、后台重启、代理超时、浏览器休眠都通过快照校正恢复；不能把“收到事件”当成数据库写入成功的唯一证明。
- 保留普通表单和 GET 页面作为无 JavaScript/无 WebSocket 降级；移动端若 WebSocket 不可用，明确显示连接失败并允许调用快照 API，不偷偷恢复高频轮询。
- 现有事件统计和日志快照报告订阅/丢弃数；界面显示连接状态并处理重连及校正，异常不回滚已提交的业务写入。

## 6. 测试计划

- 路由集成测试：HX 成功返回片段、普通请求保持 303、400/422 保留错误内容、CSRF 和会话边界不变。
- 操作集成测试：重新打包、重命名、审核、下载、元数据保存后的立即状态和后续状态更新；列表成员变化触发片段刷新。
- WebSocket 测试：未认证拒绝、hello、心跳、事件顺序、慢客户端、断线重连、序列跳跃后快照校正、多个页面订阅互不干扰。
- 移动端测试：密码与 API Key 登录、凭据到期/吊销、命令确认、重复请求、前后台恢复、切换服务器、旧响应隔离及快照校正；双方使用同一 JSON 协议样例。执行 `flutter analyze`、`flutter test`，有工具链时构建 APK，另列真实双端后端联调结果。
- 前端测试：按钮锁定、行/卡片局部更新、列表成员变化、Tag 左键/右键、替换后的重新绑定；保留输入、勾选和滚动位置；断线不触发定时整页刷新。
- 双端联调必测：WebUI 发起重打包，移动端同一作品自动更新；移动端审核/编辑，WebUI 自动更新；任务失败、恢复网络、后端重启后状态一致。提交代码和 mock 单测通过不等同真实设备验收。
- 运行受影响的 Web 集成测试、事件总线测试、JS 语法/行为测试和 `compileall`；全量回归仍按发布前要求执行。

## 9. R86 最终实现记录

- 服务端和 WebUI 已实现；移动端代码、Flutter 测试及真实设备联调属于后续阶段，不计入本次完成声明。
