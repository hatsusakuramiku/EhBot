# EHBot 重构需求说明书（v2）

> **文档性质**：重构需求基线。取代此前的 v1 需求稿。
> **重构范围**：UI 设计 + 流程控制（信息架构、实时机制、交互组件、路由分层）。
> **不在范围**：已验证的后端能力（来源链、归档流水线、安全门禁、标签翻译、幂等契约）。
> **依据**：`COMPETITIVE_ANALYSIS.md`（11 个同类项目调研 + 现状诊断）。

## 0. 为什么重构

当前实现的后端能力已经超过多数同类项目，但交互层停留在「能用」：

- 「实时进度」是 `<meta http-equiv="refresh">` **整页刷新**——同类项目无一例外都是局部更新。
- 全站**没有一张封面图**，而 Kavita/Komga/LANraragi 的主界面都是封面网格。
- 导航**平铺 9 项**，候选状态散落 4 个页面、设置散落 4 个页面，而 *arr 系用「Activity/Library/Settings + Tab」聚合。
- 仅有 **1 个 JSON API**、**16 行 JavaScript**，前端无局部更新能力。
- `app/main.py` 单文件 **88KB / 59 路由**，UI 与业务耦合，无法在其上做交互演进。

因此：**保留后端资产，重写交互层，重组信息架构与流程控制。**

## 1. 重构目标

| 编号 | 目标 | 验收信号 |
|------|------|----------|
| G1 | 封面驱动的视觉体系 | 候选主视图为封面网格，支持网格/列表切换 |
| G2 | 无整页刷新 | 全站无 `meta refresh`；进度经 JSON 轮询 + SSE 局部更新 |
| G3 | 信息架构收敛 | 顶级导航从 9 项收敛为 5 域，同类任务在域内以 Tab 组织 |
| G4 | 完整 JSON API | 每个页面数据均有对应 `/api/v1/*`，页面壳与数据解耦 |
| G5 | 流程可视化 | 单个作品从消息到入库的全链路状态在一处可见 |
| G6 | 路由分层 | `main.py` 拆为 `app/api/` + `app/web/`，单文件 < 500 行 |
| G7 | 已下载内容管理 | 独立页面列出已下载作品（网格/列表），支持勾选批量重新打包、移除、重新下载，以及单件改名/改路径 |
| G8 | 后端零回归 | 现有测试全绿，安全门禁与幂等契约不变（基线随阶段推进：R0 439 → R1 524 → R2 569） |

## 2. 目标信息架构

从 9 个平铺导航收敛为 **5 个域**：

```text
① 工作台   /                  概览、待办、连接健康度、吞吐趋势
② 候选     /candidates        [全部|待审核|待补充|已通过|驳回|失败]  ← Tab 聚合，取代 4 个独立页
③ 活动     /activity          [队列|打包|历史]                      ← 取代 下载任务 + 历史 + 打包区块
④ 已下载   /downloaded        [全部|待打包|已打包|需干预|打包失败]   ← §1.3.1，2026-08-28 恢复
⑤ 设置     /settings          [连接|来源规则|自动审批|归档|路径|AI 供应商|密码库|系统] ← Tab 聚合，取代 4 个页面
```

> **第 ④ 域的范围**：2026-08-26 曾按操作者指示整域删除，2026-08-28 依操作者指示恢复，但**只恢复 §1.3.1 列举的清单与动作**——列出已下载作品、批量重新打包/移除/重新下载、单件改名与改路径。**不做**阅读器、书架分组、导入扫描、CBZ 首图抽取封面：那些仍属下游工具。「已下载」是操作台而不是书库，作品的详情仍然只有 `/works/{id}` 一处。
>
> 活动域的「历史」与本域看的是同一批任务行，但问的不是同一个问题：历史按**任务**排列、回答「这次跑得怎么样」，已下载按**作品**排列、回答「这本书现在在哪、要不要再动它」。所以本域的分区读的是 CBZ 产物与打包任务，从不读候选状态列——打包不改候选状态，状态列答不了「打好包了吗」。

作品详情 `/works/{id}` 作为**贯穿全流程的统一详情页**：无论作品处于候选、下载中、已打包，都是同一个页面，仅底部操作区与状态时间线随阶段变化。

### 3.3 封面缩略图（新增能力）

- 候选阶段：使用 gdata 已解析的 `thumb` URL，经**服务端代理缓存**（不让浏览器直连第三方图床，避免防盗链与隐私泄露）。✅ R2
- ~~入库阶段：从 CBZ 首图抽取~~ —— 仍不实现（2026-08-28 恢复已下载域时**未**恢复这一项：已下载页复用候选阶段的封面，抽取首图要解包每一本，代价与收益不成比例）；目前只有 `card`（长边 512）一档。
- 缓存位置 `data/thumbnails/{hash前2位}/{接着2位}/{hash}.webp`，带 `ETag` 与 `immutable` 长缓存头。
- 失败时返回 **200 占位图**而不是 404（`<img>` 的 404 会渲染成碎图且无法样式化），真实状态放在 `X-Thumbnail-State` 头里，不阻塞页面。

## 4. 流程控制需求

### 4.1 实时机制（取代整页刷新）

分三级，按成本递增：

| 级别 | 机制 | 适用 |
|------|------|------|
| L1 | JSON 轮询，可见时 2s / 隐藏时暂停（`visibilitychange`） | 队列进度、打包进度 |
| L2 | SSE `/api/v1/events`，服务端在状态跃迁时推送 | 任务完成、失败、需要干预 |
| L3 | 乐观更新 + 失败回滚 | 审核通过/驳回等即时动作 |

要求：**轮询期间若后端完成，SSE 立即推送并强制刷新该行状态**（原始需求即为此意图，此前用整页刷新近似实现）。

### 4.2 统一作品生命周期

单一状态时间线贯穿全流程，在 `/works/{id}` 一处呈现：

```text
发现 → 元数据就绪 → 待审核 → 已通过 → 下载中 → 已下载 → 打包中 → 已归档
                        ↓          ↓        ↓                ↓
                    待补充/驳回   失败    等待种子/缺分卷/缺密码
```

每个节点展示：时间戳、执行者（自动规则 / 操作员 / 系统）、可回溯的原因说明、可用动作。

### 4.3 队列控制

- 队列按状态分组（进行中 / 等待中 / 需干预 / 已暂停），支持批量暂停、恢复、取消、重试、切换来源。
- 需干预项（缺分卷、缺密码、预览页缺页、种子停滞）**在工作台与队列顶部聚合提示**，不埋在列表里。
- 支持拖拽或显式优先级调整（🚧 新增，同类项目普遍具备）。
- 并发上限可在设置中调整，队列页显示当前占用/上限。

### 4.4 审核流程

- 候选页支持：多选 → 批量通过/驳回/待补充；行内快速通过；键盘快捷键（`j/k` 移动、`a` 通过、`x` 驳回）。
- 元数据编辑改为**抽屉内就地编辑**，字段显示来源标注（gdata / 翻译 / 手动），支持**字段锁定**防止后续刮削覆盖。
- 自动审批规则编辑器：条件分组、字段下拉、DSL 实时渲染预览、按字段角色的运算符/值形态校验、**对历史候选试跑并显示命中数与命中样例**（R24 起为纯类 SQL：`= / <> / > / >= / < / <= / LIKE / NOT LIKE / IN / NOT IN / EXISTS / NOT EXISTS`，`LIKE` 的 `%`/`_` 通配与 `[%]`/`[_]` 转义，匹配默认不区分大小写、逐条可选开关）。

### 4.5 已下载内容管理（§1.3.1，2026-08-28 恢复）

2026-08-26 曾整域删除，2026-08-28 依操作者指示恢复。恢复的是 §1.3.1 的清单与动作，不是书库：

| 能力 | 要求 | 状态 |
|------|------|------|
| 列表 | 单独一页展示已下载内容，可按网格/列表切换；展示标题、打包状态、文件状态 | ✅ R10 |
| 分区 | 全部 / 待打包 / 已打包 / 需干预 / 打包失败，计数与列表同源 | ✅ R10 |
| 批量打包 | 多选后批量打包；已打包的作品重新打包，**完成后替换旧打包文件**而不是并列新增 | ✅ R10 |
| 移除 | 删除下载记录，**可选**是否同时删除已下载文件；§1.2.3：**默认不移除文件** | ✅ R10 |
| 重新下载 | 按原链接重下，完成后替换旧文件；**可选**是否重新打包 | ✅ R10 |
| 改名 | 修改打包输出文件名，随即重命名磁盘上的 CBZ | ✅ R10 |
| 归档路径（单件） | 详情页直接设定库内目录与文件名：目录不存在自动创建，名称已被占用则拒绝调整（不加 ` (2)`），保存后自动重命名并移动归档文件 | ✅ R11 |
| 归档路径（批量） | 批量打包前按最新模板为每件重算路径与文件名，逐件钉住后打包 | ✅ R11 |
| 归档路径模板 | `{category}/{artist}/{title}`，保存前预览渲染结果；可按条件匹配的规则选路径模板（命中用规则模板、不命中用默认、手动钉过的路径始终优先） | ✅ R8 R25 |
| 归档路径预填 | 详情页的归档路径编辑框：已归档成功的填已保存的路径，归档失败或尚未归档的按**当前**路径规则（含按条件匹配的模板）现算；手动指定过路径的保持原样 | ✅ R27 |
| 一键重新归档 | 「设置 → 路径」整库重排：默认重排尚未成功归档的与重算路径已变动的作品，可选**强制**覆盖其余全部（含手动指定的路径）；**已打包的作品只移动、改名，不重新打包** | ✅ R27 |

四条不容含糊的语义：

- **「删记录」和「删文件」是两个决定。** 页面给的是两个按钮、两个确认对话框，不是一个带复选框的对话框——默认不删文件只有在操作员能看清自己按了哪个时才成立。忘记传标志的调用方什么都不删。
- **重新打包必须落回同一个文件。** 重新打包读已钉住的路径而不是重新渲染模板；否则改过名的书会被搬回模板位置，还会因为冲突后缀多出一个 ` (2)` 副本。R11 起权威来源是 `work_archive_paths`（以候选为键，因此第一次打包之前就答得出“这本书放哪里”），`artifacts.library_relative_path` 降为回落——它挂在产物行上，产物被移除就连路径决定一起消失；现在每次打包都会把实际落点写回这一列，好让升级上来的旧库不必迁移数据。
- **有任务在跑的作品不能移除或重下**，因为下载/打包工作线程正持有那一行。先取消，再动。
- **批量打包按最新模板重算，不合法就不动这本书。** 渲染出的路径过长或某一段含有不能用于路径的字符时，该作品既不改路径也不打包，而是落一行 `CONVERSION_WAITING_PATH` 进入需干预分组，并写明是哪一段的哪个字符——落行而不是丢一条提示，因为“这本书为什么没打包”必须明天还答得出来。这是等待态而不是失败：档案完好、什么都没尝试过，补救是改标题或在详情页钉一个路径再重排，而“重试”只会重新渲染同一个不可能的路径。操作员手填过路径的作品带 `is_manual`，模板重算绕开它：模板是默认值，默认值不推翻决定。

**不做**（与恢复前一致）：阅读器、书架/合集分组、导入扫描（只认本服务下载的内容）、从 CBZ 抽取封面、跨作品批量改名模板（归档路径模板已经是这件事）。

### 4.6 AI 供应商与模型链（2026-09-26，R28/R29/R30/R31）

运营者要求「用 AI 根据元数据决定打包后的存储位置与文件名」，并明确 **AI 路径与「按条件匹配的路径
模板」互斥，同一时间只启用一个**。设计记录在 `AI_PATH_PROPOSAL.md`；R28 落地「配好供应商」这一层，
R29 把 AI 接进路径决策（`path_source` + prompt + 指纹缓存 + 需干预/回退 + 来源标注），R30 补齐
AI 模式下的**整库重排**（计划只读缓存、需要新答案的交给「只移动不重打包」的重算路径任务、强制全库
重新询问、试跑、批量/并发/流式开关）。R31 **按 AstrBot 的管理方式重写这一层**：供应商 → 模型两层、
Key/模型批量录入、逐模型请求参数（默认不发任何参数）、配置不再有验证门槛；并引入「**全局默认模型**」
与**页面级覆盖**——AI 页拥有全局默认链，路径页可选跟随或单独指定（迁移 `019`）。

| 能力 | 要求 | 状态 |
|------|------|------|
| 供应商目录 | 单独一页、左列表右配置；多个**OpenAI 兼容**端点（名称唯一 / 编码 / 基础地址 / 超时 / 重试 / 自定义请求头 / 供应商级默认参数 / 启用） | ✅ R28/R31 |
| 多 Key 轮询 | 每个供应商多把 Key，一次粘贴批量添加（`备注:key` 或裸 key），加密存储、页面永不回显；轮询取用，401/403/429 的那把冷却 10 分钟后跳过，冷却状态落库、可手动重置 | ✅ R28/R31 |
| 可用模型 | 每个供应商一组模型名；批量手填或 `GET /v1/models` 拉取后勾选，清单里批量启用/停用 | ✅ R28/R31 |
| 逐模型请求参数 | 模型级 JSON 覆盖供应商默认值；**默认请求体只有 `model` 与 `messages`**，参数一律选填——推理模型（拒绝 `temperature`、只认 `max_completion_tokens`）与严格网关因此也能接入 | ✅ R31 |
| 配置不做验证门槛 | 未验证 / 最近验证失败 / 已停用 / 供应商无可用 Key 的模型**都能进链**；「测试」是对某个模型或整条链的按钮，失败原因与时间落库并显示，但不阻塞保存 | ✅ R31 |
| 全局默认模型 | AI 页顶部一张可跨供应商的有序链，第 0 位主力 + 备用；**其他页面不单独指定就用它** | ✅ R31 |
| 页面级模型覆盖 | 路径页「路径决策模型」二选一：跟随全局默认，或本页单独指定一条链（`ai_settings.ai_model_source`）；两张列表互不影响，链按 `scope` 分行存储 | ✅ R31 |
| AI 决定路径 | `path_source ∈ {template(默认), ai}`；AI 输出目录 + 文件名两段，`.cbz` 由本服务追加；缓存即语义（指纹 = 元数据 + prompt + 模型链 + 基础地址与请求参数，**Key 不进指纹**）；全链失败默认进「需干预」 | ✅ R29 |
| AI 路径的来源标注 | 作品详情页「归档」面板与已下载列表给 AI 产出的路径打 `AI 生成` 徽标；判定＝缓存行存在且 `relative_path` == 当前记录在案的路径（纯读、不加列，人工改名后自动消失） | ✅ R29 |
| AI 模式重排 | 计划阶段不调模型；需要新答案的按 `每批处理数量` 分批准备并入队，复用转换 worker（并发数只用于并发拉取元数据；模型调用发生在 job 内，逐件进行）；**强制＝全库重新询问**（含缓存已是当前答案的作品，并覆盖手动 pin）；已打包只移动、改名；同页提供只计划不执行的「试跑」 | ✅ R30 |
| 重算路径任务 | AI 模式下需要新答案的**已打包**作品入队为 `refile` 任务（`details_json`）：向模型（或兜底模板）问一个新路径，再把已有 CBZ 移动并改写记录，从不重新压缩；没有可用路径则停在「待定归档路径」 | ✅ R30 |
| 流式传输 | `ai_stream` 打开后模型请求走 SSE（`data: [DONE]` 收尾）；只改变传输方式，答案完全相同；供应商忽略该开关时回退读普通 JSON | ✅ R30 |

三条不容含糊的语义：

- **AI 只替代「模板 + 规则」这一层。** 审批、元数据刮削与翻译、`ComicInfo.xml`、以及「作品详情页
  手动指定的路径优先」都不动——只有「一键重新归档」的**强制**才会覆盖手动 pin（与 R27 一致）。
- **模型的回答不是可信输入。** 非法字符、保留名、超长段走 `safe_library_name` 清洗并记
  `ai_path_sanitized`（模板路径是拒绝、AI 是清洗）；只有 `..`、绝对路径、清洗后文件名为空、
  整条超长才判失败，并落 `CONVERSION_WAITING_PATH` + `AI_PATH_UNAVAILABLE`。安全不依赖 prompt 措辞。
- **元数据会离开宿主机。** 启用 AI 模式即把日文标题、社团、标签发给配置的端点；这是显式选择
  （默认关闭），并支持本地/自托管 OpenAI 兼容服务作为不外发的做法。
- **渲染路径永不调用模型。** 打包 job 与 AI 模式下需要新答案的「重算路径」job 是仅有的两个调用点；
  详情页预填、已下载列表与重排的**计划阶段**只读缓存。没有缓存或缓存已过期时，运营者侧不预填、不展示
  兜底模板的答案——那会是一个打包器不会采用的位置。
- **AI 模式下的模板与规则不生效。** 两者回答同一个问题，同时开启就等于再加一套「谁先谁后」的规则
  引擎；默认模板因此改称「兜底模板」，只在显式打开「不可用时回退」后才被使用。

### 5.4 打包任务与下载任务解耦

当前把转换任务以 `provider='CONVERSION'` 塞进 `download_jobs`，导致队列语义混乱（F5）。重构后：
- 新增 `conversion_jobs` 表承载打包任务，或在 API 层清晰分流为两个队列视图。
- 活动页以「队列 / 打包 / 历史」三 Tab 分别呈现，不再混在一个列表。

## 6. 业务边界（继承 v1，不变）

### 6.1 继续做

Telegram 监听与消息摄取、消息归并、ExHentai 元数据与中文标签翻译、候选审核、类 SQL 自动审批（R24 起，见 §4.4）、来源降级链下载、归档安全流水线、CBZ + `ComicInfo.xml` 发布、Docker 单容器部署。

**Telegram 用户账户（MTProto）**：Bot API 的 20 MB 下载上限在协议里，所以另加一条 MTProto 通道用于取回超限附件。原先「不引入 MTProto/Telethon」的判断已于 2026-08-28 按操作者要求撤销——当时的替代方案是转种子或预览页，但前者依赖有人做种、后者只有 1280px 重编码，都不能等价替代上传者的原档。Bot 仍是收消息的一端，用户账户只负责下载；小于 20 MB 的附件仍走 Bot。

### 6.2 明确不做（⛔）

- 不逐页抓取 EH 画廊本体；仅抓频道自建 telegra.ph 预览页作兜底，有张数/字节/超时上限。
- 不做 OCR、翻译、去水印、超分。
- 不做多租户、公开注册、复杂 RBAC（单管理员）。
- 不引入 Redis/Celery/PostgreSQL/消息队列集群。
- 不提供公网 HTTPS 证书自动签发；TLS/反代由部署者负责。
- 不绕过 Telegram/ExHentai 权限与风控。
- 不处理 `t.me/c/...` 频道消息链接。
- **重构新增排除**：不引入重量级前端框架构建链（保持无 Node 运行时依赖，见 §7）。

### 6.3 不可破坏的既有契约

- 审核前不下载完整文件；仅 `APPROVED`/`DOWNLOADED` 可入队。
- 元数据以 ExHentai 为唯一权威源。
- 幂等：`idempotency_key` + 唯一约束；重启恢复；重试复用同一任务行。
- 画质优先、成本其次；预览页是兜底而非默认；Archive Download 永远手动。
- 种子停滞不是失败，交由操作员决策。
- 打包是显式决策（`auto_pack_after_download` / `torrent_auto_pack` 默认关）。
- 凭据不落明文、页面不回显、日志不记录。
- 安全门禁（路径穿越、压缩炸弹、SSRF、图片魔数）不得放宽。

## 7. 技术选型（前端）

延续「无 Node 运行时」的部署约束，同时获得局部更新能力：

| 方案 | 结论 |
|------|------|
| **Jinja2 + HTMX + Alpine.js（推荐）** | 服务端渲染保留，HTMX 做局部替换与 SSE，Alpine 管理轻量交互态；静态资源随镜像分发，无构建链 |
| React/Vue SPA | 能力最强，但引入 Node 构建链与前后端契约维护成本，违背单容器轻量目标 |
| 维持现状（纯表单 + 整页刷新） | 无法达成 G1/G2/G5，排除 |

HTMX 与 Alpine 以固定版本的静态文件随镜像分发（不依赖 CDN，离线部署可用）。

## 8. 验收标准

1. 全站无 `<meta http-equiv="refresh">`；队列进度经轮询/SSE 局部更新，页面不跳动。
2. 候选主视图为封面网格，缩略图经服务端代理与缓存，首屏有骨架屏。
3. 顶级导航为 5 项；候选 6 个状态、已下载 5 个分区与设置 7 个分区均以 Tab 组织在域内。
4. `/works/{id}` 呈现完整状态时间线，含时间戳、执行者与原因。
5. 每个页面数据均有对应 `/api/v1/*`，返回统一错误体与分页结构。
6. `app/main.py` < 500 行；API 与页面路由分层。
7. 已下载页可网格/列表浏览、搜索、按打包状态筛选、勾选后批量重新打包/移除/重新下载，单件可改名与改路径；移除默认保留文件，删文件是另一个按钮；归档路径模板保存前可预览。
8. 批量操作具备全选/反选/计数与浮动工具条；破坏性操作有二次确认。
9. 自动审批规则可对历史候选试跑，显示命中数与样例。
10. 键盘可达、`aria-live` 播报、对比度合规；移动端单套导航结构。
11. 现有测试全绿（基线随阶段推进：R0 439 → R1 524 → R2 569 → … → R9 820 → R10 939；无 7-Zip 工具链的主机另有 12 项预期跳过）；新增 API 与前端交互有对应测试。
12. 安全门禁与幂等契约行为不变，回归测试覆盖。缩略图代理受同一条约束：只接受 hash，复用 SSRF 门禁与图片魔数门禁。
