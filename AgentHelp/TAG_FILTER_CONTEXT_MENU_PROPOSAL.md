# 方案：Tag 默认过滤与右键操作菜单（R86）

**状态：已随 R86 实现（2026-10-12）。** 按运营者补充要求，过滤操作改为页面内局部刷新，地址栏 URL 保持不变；全局局部刷新和 WebSocket 通信的统一方案见 [`WEBUI_PARTIAL_REFRESH_WEBSOCKET_PROPOSAL.md`](WEBUI_PARTIAL_REFRESH_WEBSOCKET_PROPOSAL.md)。本文件保留 Tag 的细节，不单独作为实现入口。

## 1. 需求与当前问题

当前 `ui.tag_list()` 在收到 `tag_hrefs` 时，会在每个 Tag 后固定渲染两个图标链接：`🔍`（过滤）与 `🚫`（排除）。候选页、已下载页确实需要这两个入口，作品详情页也把 `tag_hrefs` 传入了，因此详情页同样出现过滤操作。

本次目标：

1. 只有候选列表页和已下载列表页的 Tag 具备过滤交互；候选/已下载的所有状态 Tab 以及网格、列表两种视图沿用同一规则。
2. 作品详情页、设置页及其他只展示元数据的页面只显示 Tag 文本，不出现过滤或排除入口。
3. 在启用交互的页面，左键点击 Tag 直接按 `$tag:<值>$` 过滤。
4. 在启用交互的页面，右键点击 Tag 打开自定义菜单，由用户选择“过滤”或“排除”；排除使用现有 `$-tag:<值>$` 查询语义。
5. 过滤与排除都在当前界面添加条件、局部刷新结果，地址栏 URL 保持不变，不整页跳转。

## 2. 已核对的现状

- `app/web/templates/components/ui.html` 的 `tag_list(tags, tag_hrefs=None)` 已能生成过滤和排除 URL；不传 `tag_hrefs` 时是纯文本。
- `app/web/routes/candidates.py` 与 `app/web/routes/downloaded.py` 把 `tag_hrefs` 传给网格卡片和列表行，这两处保留过滤能力。
- `app/web/routes/works.py` 的 `render_work()` 把 `tag_hrefs` 传给作品详情页，这次移除该传递；详情页继续显示可编辑字段下的 Tag 文本。
- 原 `candidates.js`、`downloaded.js` 没有 Tag 右键菜单；R86 最终把共享行为放入 `realtime.js`，复用局部查询与连接状态。菜单样式放在 `ui.css`。
- `base.html` 已声明 `#main` 为 HTMX 刷新目标，`deps.page_layout()` 已能返回 `_fragment.html` 页面内容；可复用既有列表路由和 Jinja 渲染，不增加第二套客户端列表渲染。
- 现有 `deps.tag_hrefs()`、`search_href()` 能生成追加条件且去掉旧页码的请求地址。该地址用于后台 GET 查询；发送查询请求与浏览器跳转是两回事，无需修改地址栏。
- 现有候选/已下载筛选表单仍是普通 GET 表单；固定地址栏后，需要同步让相关筛选和分页操作保留当前界面状态。

## 3. 交互设计

### 3.1 启用范围

沿用 `tag_list` 现有 `tag_hrefs` 参数决定是否启用交互，无需额外增加同义开关：

- 候选页和已下载页传入过滤/排除查询信息。
- 其他页面不传查询信息，只渲染纯文本 Tag。

这使页面范围由调用方决定，宏本身不猜测当前路由。

### 3.2 左键

左键点击 Tag 或键盘 Enter，在当前搜索条件后追加 `$tag:<值>$`，然后通过 HTMX GET 请求当前列表并更新 `#main`。Tag 文本旁不再常驻两个图标链接。

刷新后的界面同时显示新搜索框值、条件 chips、结果列表、总数和分页，页码回到第 1 页；保留当前状态 Tab、网格/列表视图、排序、侧栏筛选和每页条数。同一条件不重复添加，带空格的 Tag 继续使用现有引号编码。

这是对整个当前状态列表进行查询，筛选后可以翻页查看所有匹配项。地址栏及浏览器历史均不因本次操作改变（不使用 `pushState`/`replaceState`，不启用 `hx-push-url`/`hx-replace-url`）。

### 3.3 右键菜单

在交互 Tag 上拦截 `contextmenu`，阻止浏览器默认菜单，打开紧邻 Tag 的菜单，包含两个操作项：

- `🔍 过滤`：追加 `$tag:<值>$`，在当前界面刷新结果；
- `🚫 排除`：追加 `$-tag:<值>$`，在当前界面刷新结果。

菜单要求：

- 菜单定位以 Tag 的屏幕位置为起点，并在靠近窗口边缘时回调到可视区域内；
- 同一时间最多一个菜单；点击菜单外、按 `Escape` 或页面滚动时关闭；
- 选择任一菜单项后关闭菜单，并与左键复用同一套局部查询流程；
- 菜单使用 `role="menu"`/`role="menuitem"`，打开后把焦点移到第一项，方向键在两项间移动，`Enter`/`Space` 激活；支持键盘的上下文菜单按键（`ContextMenu`/`Shift+F10`）打开同一菜单；
- 菜单只由启用交互的 Tag 生成，纯文本 Tag 不注册事件。

不增加“反转”“永久排除”等额外动作；本次只覆盖过滤与排除两个现有查询语义。

### 3.4 当前筛选状态与后续操作

地址栏不再代表界面最新条件，因此连续点击 Tag 时必须以当前搜索框及筛选表单的值为准，包括尚未提交的搜索输入，不能从 `window.location.search` 恢复旧条件。条件追加/编码复用现有规则，若需要后端生成查询信息，只做最小共享调整。

搜索提交、移除条件 chip、清除条件、分页、每页条数、排序及网格/列表切换沿用当前界面条件，并在这两个列表页内局部刷新，地址栏保持不变。真正切换页面或状态 Tab 仍按既有导航处理。相关批量操作后的局部刷新也需保留当前筛选状态，避免回到地址栏所代表的旧结果。

沿用既有 HTMX `show:none` 设置保持滚动位置；刷新后重新初始化列表选择、抽屉和已下载进度行为。查询失败给出可见提示，不自动整页跳转；连续操作以最后一次提交的条件为准。

### 3.5 降级与刷新行为

保留普通链接/GET 表单作为无 JavaScript 的降级路径：此时浏览器按原方式导航，右键使用浏览器默认菜单。固定地址栏和局部刷新适用于 JavaScript 与 HTMX 正常加载的使用场景。

由于不把新条件写入 URL，浏览器刷新、复制地址或重新进入页面时，只恢复 URL 原有的条件；本阶段不增加跨刷新持久化。当前界面中的条件通过搜索框与 chips 明确展示，可逐项移除或清空。

## 4. 实现边界

- 修改共享 Tag 宏及候选/已下载模板调用；详情页移除 `tag_hrefs` 传递。
- 在共享 `ui.js` 中加入最小的 Tag 菜单生命周期、键盘处理和局部查询行为，在 `ui.css` 中加入菜单定位及焦点态样式。
- 候选/已下载的筛选、分页等相关控件接入已有 HTMX 刷新机制；必要时调整候选页初始化方式和操作返回状态，使局部刷新后仍可连续操作。
- 复用现有搜索解析器、查询路由与服务端模板；URL 是后台请求地址和无 JavaScript 降级入口，不是正常操作时的导航目标。
- 保留现有 `data-tag` 属性，便于测试和无障碍检查；必要时补充 `aria-label`/`aria-haspopup`/`aria-expanded`。
- 不做数据库迁移，不改变 `$tag:` 与 `$-tag:` 的语义，不改变其他页面的 Tag 文本或元数据编辑行为。

## 7. 取舍

- v1 沿用链接跳转；v2 按运营者要求改为“界面添加条件 + HTMX 局部查询”，地址栏不变。当前列表请求仍使用现有 URL/查询参数接口，无需新建查询协议。
- 保持 URL 不变意味着新条件不会随复制链接或浏览器刷新保留，当前筛选条件以界面的搜索框和 chips 为准。
- 右键菜单是页面自定义菜单，因此会取代浏览器默认右键菜单；`Escape`、菜单外点击和滚动均可关闭，避免菜单残留。
- 详情页保留 Tag 的编辑输入与纯展示文本，但不再作为进入候选过滤列表的快捷入口；这是本次“只有候选或已下载页面需要过滤操作”的范围收窄。
