## 确认缺陷（按修复优先级）

### 1. P1：允许移除运行记录，但执行未终止，适配器还能重建已移除记录

位置：`app/downloads/archived.py:517`、`:641`；查询来源 `app/db/database.py:2715`；重新建行路径 `app/exhentai/service.py:425`、`app/telegraph/service.py:240`。

`downloaded_work` 只选择带 ARCHIVE 产物的一个下载任务。现有移除守卫既不符合运营者“运行时也可移除”的要求，也无法覆盖所有兄弟任务。更关键的是，删除任务行未通知执行器终止；EH 和预览页适配器还能自行创建任务行，不受队列最终状态检查约束。

初轮复现：同一候选有一条 COMPLETED + ARCHIVE 的 Telegram 任务，另有一条 DOWNLOADING、无产物的 EH 任务，执行 `remove_work` 成功删除 2 条任务。**补充复现**：在 EH 委托传输等待时移除这些行，数据库任务数为 0；释放传输，让实际 `ExHentaiService._record_artifact_sync` 收尾后，数据库再次出现一条 EXHENTAI / COMPLETED 任务。只使用临时文件和实际持久化逻辑，没有连接 EH。

影响：用户已移除的下载记录会复活，旧执行仍可能写文件或触发打包；带文件删除的动作还会与传输/打包输入产生竞争。彻底删除候选后也不能继续有效提交，不过是否表现为外键失败取决于具体适配器；本轮没有把 purge 的精确结果当作已复现事实。

建议：**允许运行时移除记录**，在同一操作中撤销该作品全部执行资格、阻止新认领并请求停止实际下载/打包；必须留下独立于被删记录的必要收尾信息，防止远端任务失联。将任务/产物提交权收回队列核心，旧尝试禁止重建记录、发布文件和启动下游。文件删除仍保留原有显式选项。

### 2. P1：取消只改状态，活动传输仍会完成并覆盖 CANCELLED

位置：`app/downloads/service.py:637`、`:807`、`:1368`、`:1414`。

下载 worker 等待实际 provider 调用；取消函数只更新任务行。provider 返回后，完成路径没有核对取消状态或本次尝试身份，直接写 COMPLETED 并可能自动打包。Telegram Bot/账户路径也没有运行任务的取消协调。

复现：用异步事件阻塞 EH 委托传输，在其运行期间调用 `cancel_job`，得到 CANCELLED；随后放开传输，最终任务状态变成 COMPLETED。

影响：界面承诺的取消不成立；切换来源时旧来源仍可完成；用户随后移除记录/文件时，旧传输还可能写入。

建议：协调活动传输的取消与收尾；provider 返回后、登记产物和完成状态之前核对有效尝试及当前状态，防止旧尝试覆盖取消或重试。单独在结尾补一个 SELECT 仍需考虑检查到写入之间的竞争。

### 3. P2：租约未到期时重启，任务不会在到期后恢复

位置：`app/downloads/service.py:891`、`:938`、`:971`。

`start` 仅调用一次 `reclaim_expired_leases`。任务租约为 5 分钟；进程在租约仍有效时退出并快速重启，启动恢复会跳过它。日常 worker 只领取 PENDING，不再扫描后来到期的 DOWNLOADING。

复现：领取任务后调用启动时的租约恢复，回收数为 0；将时间推进到过期，再执行正常 worker 回合，返回 False，任务仍为 DOWNLOADING。

影响：普通重启即可留下无人持有的任务，等待更久也不会自愈。可以手动取消再重试，但这不满足自动恢复目的。

建议：增加后续过期检查，同时识别本进程仍执行的尝试并续租/排除，不能直接周期回收所有过期行；实际大文件下载可能超过现有 5 分钟期限。

### 4. P2：自动审批固定读取最早 100 条，后续候选可永远不被扫描

位置：`app/auto_approval/sweeper.py:154`；`app/db/database.py:3484`。

每轮读取 `ORDER BY id ASC LIMIT 100`，没有游标或轮转记录。前 100 条画廊候选不匹配规则时继续留在 PENDING_REVIEW，后续每轮仍读同一组。改为 oldest-first 只是把原来的饥饿方向倒转。

复现：建立 101 条带画廊 ID 的待审核候选，规则编排返回“不匹配”；连续两轮共调用 200 次，但只见到 100 个不同候选，第 101 条从未被检查。规则结果用替身控制，批次选择与数据库均为实际实现。

影响：新增匹配候选、后来新增/修改的规则对窗口外的积压候选不会生效。入库回调和打开候选页可能处理部分记录，不能替代定时扫描覆盖全部积压。

建议：在批次之间轮转游标，完成一轮后重新检查旧候选；规则修改也要能重新评估未命中的候选，不宜简单永久标记“已扫描”。

### 5. P2：重下并打包先重置下载，再被打包就绪检查拒绝

位置：`app/downloads/archived.py:712`；`app/conversion/service.py:822`。

`redownload_work(repack=True)` 先把原下载行改为 PENDING，然后立即调用 conversion enqueue。后者要求 COMPLETED 下载 + ARCHIVE 产物，原行此时已不满足条件。注释所称“排在下载后面”没有对应的 worker 等待实现。

复现：候选只有一条已完成、带 ARCHIVE 的下载，调用后抛 `ARCHIVE_NOT_READY`；下载已变 PENDING，`details_json` 仍为 `{}`，没有创建打包任务。

影响：请求报失败但下载已经入队；自动打包关闭时，用户选择的下载后打包丢失。若有另一个来源的完成产物，立即入队反而可能读取旧来源，不能靠放宽就绪检查解决。

建议：在重下任务上保存本次明确的完成后打包意图，由下载完成路径消费；不要提前创建能读取旧产物的打包任务。验证自动打包关闭、下载失败和已有其他来源产物三种场景。

### 6. P2：刷新令牌的消费与新令牌签发非原子

位置：`app/api/auth.py:181`、`:194`、`:195`。

刷新流程分别读取凭据、检查撤销、撤销旧凭据、签发新凭据。两个并行请求可以同时读到未撤销状态，撤销操作也不提供“本次确实消费成功”的条件裁决，之后均签发。

复现：使用实际临时凭据表与实际签发逻辑，以屏障控制两个请求在读取旧凭据后同时继续，同一 refresh token 签出 2 对有效凭据。凭据只存在内存/临时库，没有打印或保存到报告。

影响：一次性轮换契约失效，多设备/并发重连可能形成分叉；撤销与签发之间中断也会让旧令牌失效却没有新令牌。

建议：在同一数据库事务中条件消费旧 refresh 并建立新的一对凭据；只有消费成功者可签发。并发失败者返回既有撤销类错误，测试同时覆盖并行刷新和中途失败。

### 7. P2：ComicInfo 同步持有全库写锁跨越整个 CBZ 改写与哈希

位置：`app/downloads/archived.py:339`、`:384`；`app/db/database.py:708`。

同步先 `BEGIN IMMEDIATE`，随后在该事务内复制整个 CBZ、替换文件，再读取整个文件计算 SHA-256。SQLite 是全库单写者；其他候选、任务与配置的写入最多等待 5 秒。

复现：使用实际小 CBZ 和实际同步流程，仅以事件延迟文件改写；同步持有写锁期间，另一个候选的普通 UPDATE 在超时后抛 `database is locked`，随后文件同步仍成功。

影响：大文件或慢磁盘的一次元数据保存可能让无关业务写入超时。这是故意延迟 I/O 的确定性复现，不代表已测量生产 CBZ 的实际耗时。

建议：减少全库写事务的持有时间，将昂贵文件处理与本作品的排他协调分开；提交前重新验证任务/文件身份。必须保留现有“不能被同作品 worker 认领或并发编辑抢写”的约束，不能简单删除锁。

### 8. P2：封面并发去重使用过期 PENDING 快照，仍可能重复抓取

位置：`app/thumbnails/service.py:120`、`:143`、`:298`。

每个请求先异步读取缓存行，再进入 `_ensure_fetch`。一个较慢请求可能先读到 PENDING，但等另一个请求已抓取完成、将缓存行改为 READY 并移除 `_pending_fetches` 后才继续。`_ensure_fetch` 此时看到没有活动抓取，未重读数据库状态，因而再次发出下载。

证据：本次页面/配置回归中的既有 `test_thumbnails_workflow.py::TestConcurrentFirstPaint::test_a_grid_of_identical_covers_fetches_once` 失败，8 个并发请求实际触发 2 次 GET；单独复跑该用例通过，符合调度相关故障。随后以屏障保留第二个请求的旧 PENDING 快照，用实际数据库、缩略图服务、图片转换和本地 MockTransport，稳定复现 2 次 GET，不依赖网络。

影响：重复下载和转换同一封面，增加上游请求与限流概率；同一缓存文件也发生重复写入。影响程度低于任务删除与取消，但它是已存在用例暴露的真实并发缺陷。

建议：在每个 hash 的抓取协调区内重新检查缓存状态，或共享包含最终结果的任务；不能仅依据进入前读取的 PENDING 行决定新抓取。补充“第一个请求完成后，持旧快照的请求继续”的确定性调度用例。

数据库有 `telegram_accounts` 和来源消息的账号复合键，可复用基础结构，但当前摄取统一写到 `bot-api://configured` 身份，Bot update_id/offset 全局，MTProto 来源游标仅按 chat_id 更新。直接增加几个 Token 或复制连接面板会造成消息身份/游标混淆；需要真实账号贯穿监听、observation、入队来源、attempt 与凭据版本。

已实际读取 JDownloader 官方 Account Manager/Cookie 多账号文章、pyLoad 官方账号管理/选择源码、Telegram Bot API 与 Telethon session 文档。方案新增账号 CRUD/启停/掩码查看编辑、TG 源账号路由、EH 有界轮换及费用结果不确定处理，并同步扩展共享 API、阶段、迁移与验收。TG Bot 的 file_id 不能交给其他 Bot 使用；同 EH 来源换账号也必须先收束旧尝试，作品取消/移除后不得继续账号池接替。

## 管理员登录名补充审阅

## 多账号并发与统一唯一键补充审阅

按运营者给出的“唯一键＋附加信息表”方向收敛方案：已入库候选和未入库待处理数据通过同一 unique_key 记录匹配，数据库唯一约束决定谁创建记录，处理状态/所有权保证只领取一次；所有账号观察继续保存为来源，不因重复画廊而丢掉备用下载路径。具体表草案、统一键规则与三类并发场景见整合方案 §8.3.G。

静态核对发现当前前置闸门按画廊 ID 忽略重复，而保存函数和表唯一约束按 ID＋Token；重复命中会不关联来源，解析结果还未保留转发原帖坐标。这些路径需要收口，并明确替换 R59“不并入、不追附件”的取舍，保持一个画廊一个候选。此处为设计差距及静态缺口，不新增未经复现的缺陷统计。

已读取 Telegram 官方频道/群消息盒、Bot MessageOrigin 和 MTProto messageFwdHeader 文档：频道坐标可作为跨账号统一身份，普通群/私聊需保留账号作用域，隐藏转发来源不能仅凭名称/时间认定同一原帖。方案保留这类身份不全的数据，补全后原子升级键；唯一键去重与来源账号选择分开，不能混用不同 Bot 的 file_id。
