## 0. 需求（运营者原话，2026-10-11）

> 手动添加功能怎么样？应该是点击添加 → 检查是否已存在 → 已存在进行提示是否跳转到页面；
> 不存在就进入添加流程 → 填写标题等元数据或通过 Eh 拉取元数据。手动添加需要进行限制，
> 仅支持 Eh 链接添加，添加时需要验证链接是否有效，如果未配置 Eh 连接则需要阻止并提示先配置 Eh 连接

拆成四条：

1. **入口**：点「添加」→ 先检查这件作品是否已存在；
   已存在 → **提示并给出跳转**到已有候选（不是像现在只把错误文字写在表单上）；
   不存在 → 进入添加流程。
2. **流程**：可以**填写标题等元数据**，也可以**通过 Eh 拉取元数据**。
3. **限制**：只支持 **Eh 链接**（不再接受磁力链接等其它输入）。
4. **前置**：添加时**验证链接是否有效**；**未配置 Eh 连接则阻止**并提示先去配置。

## 1. 现状（`app/web/routes/manual_add.py`，单表单一步到位）

| 现状 | 说明 |
|---|---|
| 入口 | 导航里的「手动添加」页，一个文本框 `input` |
| 接受 | ExHentai / e-hentai 画廊链接、telegra.ph 预览 slug、**磁力链接**（`_MAGNET_PATTERN`） |
| 判重 | R60 已做：`create_manual_candidate` 撞同画廊 ID / 同 infohash → `DuplicateCandidateError`，页面 409 并把 `existing_candidate_id` 传进模板 |
| 连接检查 | `_exhentai_configured()` / `_torrent_configured()` 只作为**提示**传给模板（`manual_add.html` 上有红字），**不阻止提交**（注释写明「status is a hint, not a gate」） |
| 添加动作 | `create_manual_candidate`（**已 APPROVED**）→ 立即 `fetch_metadata_for_candidate()` 拉元数据 → `_enqueue_manual_candidate()` 入队 → 303 跳作品详情页 |
| 标题 | 先写 `ExHentai #<gid>`（画廊链接）/ `磁力 <hash8>`（磁力） |

也就是说：判重、连接状态、拉元数据**都已经有了**，缺的是「先检查再进流程」的两步感、
「已存在就跳转」的交互、以及「仅 Eh 链接 + 未配置就拦下」这两条限制。

## 2. 设计

### 2.1 只收 Eh 链接（第 3 条）

- `_ingest_manual_link()` 只保留 `find_gallery_ref()` / `find_preview_gallery_ref()`；
  磁力分支（`_ingest_manual_magnet`、`_MAGNET_PATTERN`、`_torrent_configured`）**删除**，
  模板里磁力相关的提示一并删除；
- 输入不是 Eh 画廊链接 → `ReviewError("INVALID_LINK", "仅支持 ExHentai 画廊链接（e-hentai.org / exhentai.org）")`；
- 判重仍然按**画廊 ID 单列**（R59/R60 的不变量：token 不是身份），磁链判重的那条 SQL 保留给别的入口用。

### 2.2 未配置 Eh 连接就拦下（第 4 条）

- 提交时（不只是渲染时）检查 `connection_manager.snapshot().exhentai.configured`；
  未配置 → **不建候选**，返回 400 + 「未配置 Exhentai 连接，请先在『连接』页配置后再手动添加」，
  模板给出到 `/connections` 的链接；
- 页面打开时同样显示这条提示并把提交按钮置灰（`disabled`），但**服务端仍然要挡**
  （现在的 `_exhentai_configured` 只是提示，注释里也是这么写的）。

### 2.3 验证链接有效（第 4 条）

「有效」用**真拉一次**来证明，而不是只匹配正则：

1. 解析出 `(gid, token)`（形状不对 → 400「无法识别链接」）；
2. 调 `ExHentaiService.fetch_metadata_for_candidate()`（就是现在添加时做的那一步）——
   画廊不存在 / 需要登录 / 网络失败都会抛 `ExHentaiDownloadError` → 400 并把原因写在表单上，
   **候选不创建**；
3. 成功 → 元数据已经落库，标题就是画廊名（日文优先）。

这条把「验证链接」与「拉元数据」合成一次调用，不额外发请求。

### 2.4 判重与跳转（第 1 条）

- 顺序：**先校验形状 → 再查重 → 再拉元数据 → 再建候选**。查重在拉元数据之前，
  重复粘贴不会白花一次抓取；
- 已存在 → 不再显示原始错误文字，改成一张确认卡：**「作品已存在：候选 #<id>（标题）」+
  「跳转到该候选」按钮 + 「返回」**。`existing_candidate_id` 现有字段够用，
  只是模板要从「红字」升级成「可点的确认块」（`ui.confirm` 已有的样式沿用）；
- 跳转目标就是现成的 `/works/<id>`。

### 2.5 添加流程：填元数据或从 Eh 拉（第 2 条）

**推荐：不新建一套元数据表单，把操作者送到作品详情页**——那里已经有：

- 逐字段编辑（`POST /candidates/<id>/metadata`，`work_detail.html:201`）；
- 「拉取元数据」按钮（`POST /works/<id>/exhentai-metadata`，`work_detail.html:434`）；
- 时间线里能看到这次抓取发生了什么。

所以流程是：`校验 → 查重 → 拉元数据 → 建候选（已审批）→ 入队 → 303 到 /works/<id>`，
操作者在那页补/改标题等元数据，或再点一次「拉取元数据」。这与「填写标题等元数据或通过 Eh
拉取元数据」等价，而且不会出现第二套字段表（第二套就要跟着 `METADATA_FIELDS` 一起漂）。

若你确实想要**独立的两步表单**（先填标题再落库），那是另一版设计，我不推荐：字段表会变成第二份真源。

### 2.6 标题（与 v6 一致）

- 手动添加先写占位 `#<gid>`，拉元数据成功后由画廊标题（日文优先）顶掉；拉不到就把占位换成
  `#<gid>` 兜底（v6 §2.4），候选仍可人工补；
- 手动添加是**已审批直接入队**，不经过待补充——这条与 v6 的「无标题进待补充」是有意的例外，
  因为手动添加本来就是操作者发起的（见 §4 待确认 2）。
