{# 自动审批 tab: the rule editor, and the trial run that says what a rule would do before it is allowed to do it. A rule that fires approves a candidate for download without an operator seeing it, so the editor is built around not being able to save something you have not checked. The condition rows and the two buttons are ONE form: 试跑 and 保存 submit the same fields to different `formaction`s, so what was tried is exactly what gets saved -- a separate preview form could drift from the editor above it by a character and still look right. A row is either a comparison (`{Field} OPERATOR value`) or a regex (`Regex({Field}, 'pattern')`). Rows are combined by the group operator into the `group` node `validate_rule_ast` already understands. One row saves as itself rather than as a group of one, so a simple rule reads simply in the DSL. Field and operator lists come from `vocabulary`, built in `app/api/settings.py` from the engine's own tables. A field the evaluator does not support therefore cannot be offered -- the dropdown cannot drift from `ALLOWED_FIELDS`, because it is generated from it. Live syntax checking is `settings.js` and is a convenience only. The save handler validates through `validate_rule_ast` regardless, so an invalid regex is refused whether or not JavaScript ran. #} {% macro condition_row(index, vocabulary) -%} {#- One condition. Rows submit as parallel lists (`condition_kind` and friends), which is what an HTML form does natively with repeated names -- no JSON in a hidden field, so the rows survive with JavaScript off. A row whose field is blank is skipped server-side, which is how the extra empty row costs nothing. -#}
