Both the add form and each stored row post to the same `configure_source` endpoint, keyed by `(account_id, chat_id)` -- which is why the row form carries that identity as hidden fields and does not let it be edited. Changing a chat id would mean creating a different source, and doing it through an「更新」button would silently orphan the old one. Two batch paths sit beside the single forms, both built on HTML's `form="…"` attribute rather than JavaScript or a second nested form (which HTML forbids): * 会话列表 -- one checkbox per row belongs to the hidden `#dialog-batch-add` form, so several chats can be created in one submit, all disabled, with an empty rule set. * 已配置来源 -- one checkbox per row belongs to `#sources-batch`, whose buttons enable, disable, tombstone (删除) or overwrite the filter rules of everything selected. 删除 is a tombstone rather than a DELETE because `discover_telegram_source` re-creates a row for any chat a message arrives from; a dismissed row stays hidden until the chat is saved again on purpose. The filter lists submit as comma-separated text because that is what an operator types; the snapshot returns them as arrays, so `join(', ')` here is rendering, not parsing. A Chat ID is a number only Telegram knows, so the add panel can also read it out of the logged-in user account's own dialog list (`POST /sources/dialogs`) and offer that account's channels, groups and private chats as a pickable list.
